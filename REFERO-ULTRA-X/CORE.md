# CORE — System Constitution

## 1. Source hierarchy

When sources conflict, use:

1. Explicit current user requirements
2. Existing product and technical constraints
3. Current project documentation
4. Current Refero research
5. Verified domain/product constraints
6. Proven craft and established patterns
7. Creative exploration
8. Generic model preference

## 2. Intent preservation

Every meaningful statement from a brain dump must be classified as:

- requirement
- constraint
- preference
- idea
- reference
- question
- assumption
- conflict
- unresolved
- out-of-scope

Do not silently delete ambiguity. Resolve it, record it, or preserve it as an open decision.

## 3. Research-first

Research should answer decisions, not merely collect inspiration.

Use:
- Refero Styles for visual systems and directions.
- Refero Screens for concrete UI patterns.
- Refero Flows for multi-step journeys.
- Creative-web research for high-craft, cinematic, experimental, or Awwwards-level interaction.
- Existing project research for continuity.

## 4. Reference synthesis

Never create a visual direction by averaging unrelated references.

For every selected reference, identify:
- what is borrowed;
- why it is relevant;
- what is explicitly rejected;
- which layer it influences.

## 5. System thinking

Design:
- visual tokens;
- layout rules;
- typography;
- component grammar;
- content hierarchy;
- state behavior;
- responsive art direction;
- motion;
- accessibility;
- performance.

## 6. Creative excellence

For high-impact work, run `CREATIVE-EXCELLENCE.md`: define a distinctive creative thesis, explore materially different directions, and identify a signature moment before implementation. Do not default to generic patterns when the brief calls for a memorable experience. Balance expressive moments with calm, usable areas.

## 7. Image-to-code fidelity

A screenshot is evidence, not a complete specification. For reference-led work, use `IMAGE-TO-CODE.md`: inspect the source, compile a visual specification, map assets and geometry, implement against the spec, render at matching viewports, compare, and iterate. Never equate image understanding or successful compilation with faithful visual implementation.

## 8. Reference intelligence and motion evidence

For reference-led work, distinguish observed facts from inferences and unknowns. Analyze a reference by role and by the specific layer it informs; never treat a thumbnail as evidence for an entire experience. For motion-heavy work, capture state transitions and triggers, not just endpoints. See `REFERENCE-INTELLIGENCE.md` and `MOTION-RECONSTRUCTION.md`. Use `BENCHMARK-SUITE.md` for repeatable skill validation.

## 9. Documentation as infrastructure

Documentation is not an afterthought. It is part of the product engineering system.

The system must remain understandable when:
- the chat context is gone;
- another model opens the project;
- another developer joins;
- the user switches from Claude to Codex or another agent;
- a project is revisited months later.

## 10. Second Brain

The Second Brain stores reusable knowledge across projects:
references, patterns, decisions, failures, outcomes, research, client preferences, and lessons.

## 11. Memory firewall

Old knowledge may inform decisions but must not silently override current project requirements.

## 12. Quality

Every implementation should be evaluated against:
- intent;
- reference lock;
- design system;
- interaction model;
- responsive behavior;
- accessibility;
- performance;
- originality;
- maintainability.


## 13. MCP execution contract
For ambitious UI work, live Refero MCP research is a hard gate unless the user explicitly opts out. Discover current tools and schemas, search multiple queries across available styles/screens/flows, inspect details, evaluate at least five candidates when possible, and create a project-local research record. If the MCP cannot be called, disclose that and use available fallbacks without pretending the MCP was used.
